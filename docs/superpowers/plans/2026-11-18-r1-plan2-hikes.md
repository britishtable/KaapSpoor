# R1 Plan 2 — Hikes (trail history, accounts in the app, sync) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the one-entry-per-route journal with hike records (many per route, with visibility, Start/Finish), let users sign in from the app, and sync hikes with the server, offline-first.

**Architecture:**
- **Server.** `/api/v1/hikes` is an idempotent upsert keyed on the client's UUID, plus a per-user change feed for pulling. Conflicts resolve last-write-wins on the client's `updatedAt`, clamped to the server clock. Deletions are tombstones and are final.
- **Client storage.** Hikes and per-route planning notes live in IndexedDB for everyone, signed in or not. A one-time upgrade converts the old journal.
- **Client sync.** A sync engine pushes pending hikes and pulls the feed when there's a reason to: sign-in, coming back online, a local write, or the app becoming visible. It never polls.

**Tech Stack:** Server as in plan 1 (Java 21, Spring Boot 3.5.3, PostGIS, Flyway, Testcontainers). App: SvelteKit + Svelte 5 runes, `idb` 8, `fake-indexeddb` for tests, the generated `openapi-fetch` client from plan 1, Vitest + Testing Library, Playwright.

**Spec:** `docs/superpowers/specs/2026-11-18-platform-and-release1-design.md`: §6 (offline-first writes, auth, route identity), §7.5 (trail history), §8 (UX principles). It also uses the follow-ups doc, `docs/superpowers/specs/2026-11-18-r1-plan1-followups.md` (first section and "Client auth handling").

## Global Constraints

**Server**
- Package root `za.kaapspoor.server`. Endpoints live under `/api/v1`. Errors are RFC 9457 `ProblemDetail`. User-safe 400s use `web.BadRequestException`.
- Route ids are the strings from `app/src/lib/data/ids.ts`, never re-derived. A hike may reference any row in `route`, including retired ones.
- Every API change regenerates the snapshot and the client in the same commit: `./mvnw test -Dtest=OpenApiSnapshotTest -Dopenapi.update=true`, then `cd ../app && npm run gen:api`. CI fails on drift.
- Every test class that deletes from `app_user` must delete from `hike` first, because of the foreign key. Today that is `PasswordAuthFlowTest`, `OidcAuthFlowTest`, `IdentityPersistenceTest`, `TokenServiceTest` and any other `delete from app_user`; grep for it.

**Hikes and sync**
- Hike visibility is `PRIVATE` (default) | `FRIENDS` | `PUBLIC`. Notes visibility is separate, with the same values and default `PRIVATE`. In R1 visibility is stored only: no screen shows anyone else's hikes (§7.5).
- Hikes are local-first for everyone. Browsing, maps and the local hike log need no account. An account is only needed to sync (§6).
- Sync conflict rule: last-write-wins per hike on `updatedAt`. Deletion is final.

**Client and UX (§8)**
- **Copy is calm and plain.** Offline is a normal state. A queued hike says "Will send when you have signal". Input is never lost.
- **Field use:** touch targets ≥ 48 px, and new trail-screen actions (Start/Finish hike) are full-width buttons.
- **Battery:** no polling loops and no `setInterval`. Sync runs only on events.
- **Design:** new screens follow the existing visual language. Load the `frontend-design:frontend-design` skill for the new `/account` page and the hike log component.

**Process**
- Commits carry **no `Co-Authored-By` trailer** (user preference).

**Schema (`V4__hike.sql`):**
```sql
alter table app_user add column hike_revision bigint not null default 0;

create table hike (
    id                uuid primary key,             -- client-generated
    user_id           uuid not null references app_user (id),
    route_id          text not null references route (id),
    hiked_on          date,                         -- null = date not recorded
    notes             text not null default '',
    visibility        text not null check (visibility in ('PRIVATE', 'FRIENDS', 'PUBLIC')),
    notes_visibility  text not null check (notes_visibility in ('PRIVATE', 'FRIENDS', 'PUBLIC')),
    plan              jsonb,                        -- {approach?, main?, exit?, reversed}
    started_at        timestamptz,
    finished_at       timestamptz,
    client_updated_at timestamptz not null,         -- LWW key, already clamped
    deleted_at        timestamptz,
    revision          bigint not null,              -- per-user, from app_user.hike_revision
    received_at       timestamptz not null
);

create index hike_user_revision_idx on hike (user_id, revision);
create index hike_route_id_idx on hike (route_id);
```

**API (all require auth):**
- `PUT /api/v1/hikes/{id}`
  - Body `HikeWrite`: `routeId` (required), `date` (ISO date or null), `notes` (required, may be ""), `visibility` (required), `notesVisibility` (required), `plan` (`HikePlan` or null), `startedAt` and `finishedAt` (instants or null), `updatedAt` (required instant), `deleted` (required boolean).
  - Always returns **200** with the server's current `Hike` for that id, whether or not the write won. The client stores whatever comes back.
- `GET /api/v1/hikes?since={long, default 0}&limit={int, default 500, max 500}`
  - Returns `HikeChanges { hikes: Hike[], next: long, hasMore: boolean }`: the caller's hikes with `revision > since`, ascending, tombstones included.
  - `next` is the last returned revision, or `since` when the page is empty.
- `Hike` = every `HikeWrite` field, plus `id` (uuid) and `revision` (long), all required in the OpenAPI schema. `date`, `plan`, `startedAt` and `finishedAt` are nullable.
- `HikePlan { approach?: string, main?: string, exit?: string, reversed: boolean }`. It mirrors `JournalPlan` in `app/src/lib/data/types.ts`.

**Rules `HikeService.upsert(UUID userId, UUID id, HikeWrite w): Hike` enforces, inside one transaction:**
1. The user is missing or soft-deleted → 401, as in `MeController`.
2. **Ordering lock.** Lock the user's row first, with `select hike_revision from app_user where id = ? for update`.
   - Only when rule 7 decides to write does the service take the next revision with `update app_user set hike_revision = hike_revision + 1 where id = ? returning hike_revision`.
   - The row lock serialises one user's writes, so revisions commit in order and a pull never skips one.
3. **Validation** (400 via `BadRequestException`, each with a plain-language detail):
   - `routeId` must exist in `route`. Retired routes are accepted.
   - `notes` ≤ 5000 chars.
   - `date` must lie between `1950-01-01` and today in `Africa/Johannesburg` plus 1 day.
   - `finishedAt` requires `startedAt`, and `finishedAt` must not be before `startedAt`.
   - Each plan id ≤ 200 chars.
4. **Ownership.** The id exists for another user → 409 "This hike id is already in use."
5. **Clamp.** `effectiveUpdatedAt = min(w.updatedAt, now)`, where `now` is the server clock (inject a `java.time.Clock` bean so tests can fix it).
6. **Tombstones win.** The stored row is a tombstone → return it unchanged, with no new revision.
7. **Last write wins.** The stored row's `client_updated_at` is newer than `effectiveUpdatedAt` → return the stored row unchanged, with no new revision. Otherwise (new, or equal and idempotent, or older) write every field, set `revision`, `received_at = now`, and `client_updated_at = effectiveUpdatedAt`.
8. **Delete.** `w.deleted = true` writes a tombstone: `deleted_at = now`, `notes = ''`, `plan = null`. The route, date and visibility are kept.

    id: string;              // crypto.randomUUID()
    routeId: string;
    date: string | null;     // YYYY-MM-DD; null = date not recorded

- Produces: `convertJournal(entries: unknown[], now: string, newId: () => string): { hikes: Hike[]; routeNotes: RouteNotes[] }` in `convert.ts`. It is pure; Task 4's v1 import reuses it.
  - Each entry is read leniently:
    - `routeId` must be a non-empty string, or the entry is skipped.
    - `done` is truthy or not.
    - `date` is used only if it is a `YYYY-MM-DD` string, else `null`.
    - `notes` is used if it is a string, else `''`.
    - `plan` is kept only if it passes the same check `isPlan` in `io.ts` uses (move `isPlan` into `convert.ts` and export it).
  - A `done` entry → one hike:
    - `date` from the entry, `notes ''`, both visibilities `PRIVATE`, `plan` from the entry;
    - `startedAt`/`finishedAt` null, `updatedAt now`, `deleted false`, `owner null`, `pending true`.
  - Any entry with non-empty notes or a plan → `RouteNotes { routeId, notes, plan, updatedAt: now }`.
  - The plan is copied to both the hike and the route notes. The old plan was recorded when Done was ticked, so it says which way the hike went, and it is also the user's saved plan.
  - An entry that is not done, with empty notes and no plan, produces nothing.
- Produces, in `db.ts` (DB name `kaapspoor`, **version 3**):
  - Stores: `hikes` (keyPath `id`, index `byRoute` on `routeId`), `routeNotes` (keyPath `routeId`), and `meta` (out-of-line string keys, any value).
  - Upgrade from `oldVersion < 3`: if store `journal` exists, read all its rows with the upgrade transaction, run `convertJournal`, write the results, then `deleteObjectStore('journal')`. Everything happens in the one versionchange transaction, so a throw aborts it and leaves v2 intact.
  - Exports:
    - `putHike(h: Hike)`, `getAllHikes(): Promise<Hike[]>`;
    - `putRouteNotes(n: RouteNotes)`, `getAllRouteNotes(): Promise<RouteNotes[]>`;
    - `replaceAllData(d: { hikes: Hike[]; routeNotes: RouteNotes[] })`, which clears and writes both stores in one transaction;
    - `getMeta<T>(key: string): Promise<T | undefined>`, `setMeta(key: string, value: unknown)`;
    - `resetDbForTests(opts?: { convert?: typeof convertJournal })`, which closes the connection and nulls the cached promise so tests can reopen at a chosen version. The optional `convert` replaces the converter that the next upgrade uses. ESM spies can't intercept a module's internal call, so this is the seam.

- Produces, in `session.ts`:
  - **Types:**
    - `SessionUser { id: string; displayName: string; initials: string }`
    - `StoredSession { accessToken: string; accessExpiresAt: string; refreshToken: string; user: SessionUser }`
    - `TokenStorage { load(): StoredSession | null; save(s: StoredSession): void; clear(): void }`
    - `localTokenStorage` is the default implementation, using `localStorage` key `kaapspoor.session`. Every access sits in try/catch; unavailable storage acts as signed out. Plan 6 swaps in native secure storage.
  - **Store:** `session: Readable<SessionUser | null>`. Every change also sets Task 4's `viewer` to the user id or null.
  - **Sign-in functions:**
    - `configureSession(opts?: { storage?: TokenStorage; fetch?: typeof fetch; baseUrl?: string | null }): void` is used by tests.
    - `restoreSession(): void` loads from storage.
    - `signIn(email: string, password: string): Promise<void>` and `register(email: string, password: string, displayName: string): Promise<void>` call `/auth/login` or `/auth/register`, then `GET /me`, and save.
    - On failure they throw `SessionError { message: string }`, carrying the ProblemDetail `detail`, or "Can't reach KaapSpoor right now. Check your signal and try again." on a network error.
    - `signOut(): Promise<void>` POSTs `/auth/logout` best-effort, clears storage and sets `session` null. **Local hikes stay.**
  - **Tokens and API access:**
    - `getAccessToken(): Promise<string | null>` refreshes first when `accessExpiresAt` is within 30 s.
    - Refreshes are **single-flight**: concurrent callers share one refresh.
    - `api()` returns `createApiClient(baseUrl, getAccessToken)`, or null when `apiBaseUrl()` is null.
  - **Refresh-failure rule** (the follow-ups doc's grace window). On a refresh 401, re-read storage:
    - if the stored refresh token differs from the one just sent (another tab rotated it), adopt the stored session and retry the request once;
    - otherwise clear the session (signed out).
    - A network error during refresh keeps the session and returns the current token.
  - **Expired-token retry.** A data request that gets 401 whose `WWW-Authenticate` contains `invalid_token` forces one refresh and retries once. A second 401 signs out. ### Task 7: Sync engine

**Files:**
- Create: `app/src/lib/sync/sync.ts`, `app/src/lib/sync/sync.test.ts`
- Modify: `app/src/routes/+layout.svelte` (call `startSync()` on mount)
- Modify: `app/src/lib/components/HikeLog.svelte` (pending copy), `app/src/routes/account/+page.svelte` (status line), and their tests

**Interfaces:**
- Consumes: Task 4's `hikes`, `applyServerHike`, `onLocalWrite`, `getMeta` and `setMeta`; Task 6's `session` and `api()`; Task 2's endpoints via the generated client.
- Produces:
  - `syncNow(): Promise<void>` is single-flight. A call during a run schedules exactly one more run after it.
  - `startSync(): () => void` wires the triggers and returns a teardown.
  - `syncState: Readable<{ status: 'off' | 'idle' | 'syncing' | 'offline' | 'error'; pendingCount: number; lastSyncedAt: string | null }>`.
    - `'off'` means signed out or no API.
    - `pendingCount` counts visible pending hikes the current user may upload.

**Algorithm** (one run, when `session` is non-null and `api()` is non-null):
1. **Push.** For every hike with `pending && (owner === null || owner === me)`, send `PUT /api/v1/hikes/{id}` with the `HikeWrite` fields.
   - **200:** if the local hike's `updatedAt` is unchanged since the request was built, `applyServerHike({ ...server, owner: me, pending: false, syncError: undefined })`. Otherwise mark only `owner: me` and keep it pending.
   - **400/409:** keep the local hike, set `pending: false` and `syncError` to the ProblemDetail `detail`. The data stays, and the next edit re-queues it.
   - **401:** stop the run. The session has already decided.
   - **Network error:** stop the run and set status `'offline'`.
2. **Pull.** Read `since` from meta key `syncCursor:{me}` (default 0). `GET ?since=` repeats while `hasMore`. For each server hike:
   - if there is no local hike, or the local one is not pending, or `server.updatedAt >= local.updatedAt` → `applyServerHike({ ...server, owner: me, pending: false })`;
   - otherwise (local pending and newer) keep local.
   - Save `next` to meta after each page.
3. **Finish.** Set `lastSyncedAt` and status `'idle'`.

**Triggers in `startSync`** (no timers except the 2 s debounce):
- `session` becomes non-null;
- `window` `online`;
- `document` `visibilitychange` to visible;
- `onLocalWrite`, debounced 2 s;
- a `navigator.onLine === false` check before a run sets `'offline'` without trying.

**UI copy:**
- `HikeLog`, pending hike while signed in:
  - "Will send when you have signal" when status is `'offline'`;
  - "Not synced yet" otherwise;
  - nothing when `syncState.status === 'off'`.
- Account page status line:
  - "All hikes synced" when `pendingCount === 0`;
  - "{n} hike(s) waiting to sync", with correct pluralisation;
  - plus "Last synced {relative time}" when `lastSyncedAt` is set.
